## 0. 给执行 Agent 的第一句话

OpenJob 的目标不是做一个“替用户无人值守海投的机器人”，也不是做一个多租户在线招聘 SaaS。它要成为一个**本地优先、事实可追溯、人工掌握最终发送权、能够长期稳定使用的个人求职工作台**：

```text
岗位发现 → 去重与筛选 → JD 理解 → AI 推荐 → 选择真实证据
→ 生成岗位定制材料 → 事实校验 → 人工审核 → 明确确认后发送
→ 记录结果 → 监测回复 → 管理面试与复盘
```

实现时必须同时满足两件事：

1. 对本人来说，日常使用要少重复操作、状态清楚、失败可恢复；
2. 对从 GitHub 拉取项目的其他用户来说，不能依赖本人的姓名、学校、简历、素材库、城市、岗位关键词、Chrome 会话或本地路径。

**优先保证正确、可解释、可恢复，再追求自动化和视觉效果。** 不要为了“功能看起来完整”而绕过人工确认、事实来源白名单、平台能力边界或安全认证。

# 2. 产品定位与业务背景

## 2.1 产品定位

OpenJob 是：

> **个人本地优先的 AI 求职运营工作台。**

它帮助一个求职者长期管理从“发现机会”到“投递后跟进”的全过程，但不替用户承担最终对外承诺。AI 的定位是：

- 处理大量岗位文本；
- 给岗位排序和解释匹配原因；
- 从权威事实中推荐适合的经历；
- 生成可编辑的岗位定制内容；
- 在发送前进行事实和安全检查。

AI 不是：

- 用户身份的代言人；
- 事实的创造者；
- 发送授权人；
- 对平台规则和账号风控负责的替代者。

## 2.2 典型业务场景

### 场景 A：日常发现实习岗位

用户在专用 Chrome 中登录招聘平台，配置城市、关键词、岗位类型和过滤条件。工作台在用户启动期间按计划时间运行一次采集，结束后停止，不占用整天电脑，不在错过时间后补跑。采集结果去重入库，可选择自动评分，但不自动发送任何消息。

### 场景 B：审核高匹配岗位

用户打开岗位池，看到岗位来源、采集时间、岗位类型、薪资、地点、JD、平台能力、评分维度和推荐素材。用户能够理解“为什么推荐”，也能看到哪些条件没有证据支持，而不是只看到一个神秘总分。

### 场景 C：生成岗位定制简历

用户选择真实简历底稿和真实素材库中的事实片段。系统只允许对事实做结构调整、表达压缩和 JD 对齐，不新增未经来源支持的经历。每一条改写都能追溯到底稿或素材条目，生成结果可编辑、可导出、可留作该岗位版本，但不能成为未来事实源。

### 场景 D：生成并发送招呼语

系统根据 JD 提取匹配点，选择有证据的真实经历，生成简短招呼语。发送前显示文本、事实引用、风险检查、平台和发送对象。用户逐条或按明确筛选条件批量确认；确认后才允许平台自动化执行。发送失败、跳过、已发送和平台拒绝都必须记录。

### 场景 E：投后跟踪

用户查看哪些岗位已发送、等待回复、已回复、需要人工跟进、已约面、已拒绝。回复监测只读取授权的专用平台会话；任何回复内容都不得自动发送，最多生成待审核建议。

### 场景 F：换一个用户安装项目

新用户从 GitHub 拉取代码，复制示例配置，上传自己的真实简历底稿，下载并填写自己的素材库模板，或者导入任意 Excel。系统应通过首次运行向导告诉他哪些配置缺失、哪些数据仍是空白，并且在没有真实来源时明确禁止生成可发送的个性化内容，而不是悄悄使用示例资料。

## 2.3 目标用户

- 需要持续求职、实习或校招投递的个人用户；
- 希望保留本地数据和账号控制权的用户；
- 愿意在发送前审核内容的用户；
- 有自己的简历底稿、经历、项目、奖项或证书材料的用户。

## 2.4 非目标用户

- 希望完全无人值守批量海投的人；
- 需要云端团队协作、企业招聘管理、统一账号池的人；
- 需要在没有真实履历的情况下自动生成可信身份的人；
- 需要破解平台验证码、绕过登录保护或规避平台风控的人。

# 4. 总体架构目标

## 4.1 分层结构

在现有结构上逐步增强，不要为了“架构好看”整体重写：

```text
Frontend React/TypeScript
    ↓ HTTP JSON API
Bottle Web Server / API Boundary
    ↓
Use-case services / task runner / scheduler
    ↓
Collection / scoring / resume engine / sender / monitor
    ↓
SQLite + filesystem artifacts
    ↓
专用 Chrome / 招聘平台 / AI Provider
```

建议最终明确以下职责：

- `src/openjob/web/server.py`：HTTP 路由、输入校验、响应格式和鉴权边界；不要继续把所有业务逻辑堆在路由函数中；
- `src/openjob/web/tasks.py`：工作台任务生命周期、互斥和取消；
- `src/openjob/web/scheduled_collection.py`：定时计划解析、时间点去重、跳过规则；
- `src/openjob/scheduled_collection_store.py`：计划运行的原子 claim 和持久化；
- `src/openjob/collection/`：平台采集与能力声明；
- `src/openjob/ai/`：评分、招呼语、简历生成和事实校验；
- `src/openjob/ai/resume_engine/`：底稿、素材、JD、匹配、版本和导出；
- `src/openjob/executor/`：发送和监测执行；
- `src/openjob/db.py`：SQLite 连接、迁移和查询，不继续无限增加无组织的全局函数；
- `src/openjob/browser/`：浏览器连接、诊断和会话，不在业务模块直接操作 CDP 细节；
- `src/openjob/notify.py`：桌面通知抽象；
- `src/openjob/config.py`：配置 schema、默认值、敏感字段处理和版本兼容。

## 4.2 长期稳定运行原则

- Web 服务主线程不执行耗时采集、AI 或发送；
- 后台任务必须可查询、可取消、可恢复或明确失败；
- 一个 Chrome 会话同一时间只能被一个平台任务占用；
- SQLite 写入要短事务、明确索引和一致的连接关闭；
- 任务状态不能只存在内存；
- 进程重启后必须把无法确认的运行标记为 `stopped`/`interrupted`，不能伪装成成功；
- 外部平台动作必须有幂等/去重策略；
- 所有外发动作必须有审计记录。

# 5. 统一业务对象与状态机

## 5.1 岗位状态

统一前后端状态名称和显示文案：

```text
pending       待评分
scored        已评分
filtered      已过滤
ready         待确认
approved      已确认待发送
sent          已发送
replied       已回复
resume_sent   简历已发
needs_resume  待手动发简历
follow_up_sent 已跟进
rejected      已拒绝
error         失败
skipped       已跳过
```

状态迁移必须白名单化。所有非法迁移返回可读错误，并保留原状态。例如：

- `pending → scored/filtered/error`；
- `scored → ready/filtered`；
- `ready → approved/rejected/skipped`；
- `approved → sent/error/skipped`；
- `sent → replied/resume_sent/follow_up_sent`；
- 不允许 `sent → pending`；
- 不允许“生成了简历”直接等价于“已发送简历”；
- 手动在平台外发送必须走 `manual_sent` 或既有等价记录，不伪造自动发送。

## 5.2 任务状态

采集、评分和发送任务都应有一致生命周期：

```text
created → preflight → running → pausing → paused
running → completed
running → stopped
running → failed
```

每种终态都要有：

- started_at；
- updated_at；
- finished_at；
- 当前阶段；
- 已处理数/总数；
- 错误数；
- stop_reason 或 error；
- 可安全展示给用户的摘要。

## 5.3 计划采集状态

单个日期+时间槽只能存在一条记录，建议状态：

```text
claimed → running → completed
claimed → skipped
claimed → failed
running → stopped   # 工作台重启或进程意外终止后收敛
```

必须防止：

- 工作台重启后同一时间点重复执行；
- 多个线程同时 claim；
- 人工任务运行时定时任务抢占 Chrome；
- 时间修改造成同一槽位重复运行；
- 失败后无限重试。

## 5.4 事实来源等级

所有面向用户的个性化输出都要携带来源类型和可追溯 ID：

| 来源 | 是否可作为事实 | 用途 |
|---|---:|---|
| 用户确认的真实简历底稿 | 是 | 个人信息、经历、技能、项目、教育等 |
| `resume_materials.xlsx`/用户任意 Excel 导入后的已确认条目 | 是 | 事实片段和 STAR 证据 |
| 用户在界面明确确认的编辑 | 是，但需记录确认时间 | 修正/补充事实 |
| 岗位 JD | 否 | 需求、关键词、匹配目标 |
| AI 岗位评分理由 | 否 | 推荐哪些已有素材 |
| AI 生成定制简历 | 否 | 岗位版本产物，不可反哺 |
| BOSS 平台默认招呼语 | 否 | 平台账号配置文本，非 OpenJob 事实 |
| `resume.md`/`resume.example.md`/示例数据 | 否 | 仅演示或模板 |

# 7. 阶段 0：基线、术语和架构冻结

## 目标

让所有后续 Agent 在同一套产品规则下工作，避免“招呼语能用一套事实、简历又用另一套事实”“页面显示已发送但数据库仍待确认”等问题。

## 执行任务

### 0.1 建立产品契约

新增或完善一份开发者契约文档，至少写清：

- 产品定位；
- 不自动发送的边界；
- 真实事实源白名单；
- 示例数据排除规则；
- 平台能力矩阵；
- 数据目录和敏感字段；
- 任务状态和岗位状态；
- 错误码和响应格式；
- 兼容性和迁移原则。

### 0.2 统一常量

将状态标签、平台能力、来源类型、导入状态、任务终态集中管理。前端不要自行复制一份含义不同的常量。

### 0.3 统一 API 响应

建议标准：

```json
{
  "success": true,
  "data": {},
  "error": null,
  "request_id": "..."
}
```

错误：

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "PRECHECK_BROWSER_OFFLINE",
    "message": "专用 Chrome 未连接",
    "retryable": false,
    "details": {}
  },
  "request_id": "..."
}
```

兼容现有 API 时可渐进接入，但新增接口不得随意返回不同结构。

### 0.4 数据目录契约

# 8. 阶段 1：核心采集、评分和任务稳定化

## 目标

把“采集一次并得到可审核岗位列表”做成可以每天重复使用的可靠流程。

## 8.1 采集

- 采集前 preflight 检查：Chrome/CDP、平台登录态、关键词、城市、岗位类型、页面额度、风控锁；
- 每个岗位保留 `source_platform`、原始 URL、采集时间、搜索关键词、城市和采集批次；
- JD 原文与清洗文本分开保存；
- 失败不覆盖已有有效字段；
- 平台选择器失败时记录可诊断错误，不把空结果当成“没有岗位”；
- 采集过程支持取消，取消后状态可收敛；
- 同一任务不得并发启动两个 Chrome 采集器。

## 8.2 去重

去重优先级建议：

1. 平台岗位唯一 ID；
2. 平台 + 规范化 URL；
3. 公司 + 职位 + 城市 + JD 摘要指纹；
4. 不能确定时标记疑似重复，让用户决定。

不要因 JD 小幅变化误删新岗位。保留最后采集时间和来源批次。

## 8.3 评分

评分必须展示：

- 总分；
- 各维度分数；
- JD 要求；
- 命中的真实证据 ID；
- 未找到证据的要求；
- 硬性否决项；
- 评分模型、时间和版本；
- “推荐素材”与“事实证明”两个概念的明确区分。

如果没有真实底稿或素材，评分仍可对岗位做通用匹配，但不得由评分结果创造个人事实。

## 8.4 失败和恢复

- 网络/平台临时错误：有限次数、指数退避或现有节奏策略；
- 选择器错误：停止该平台，保留已采集结果；
- AI 超时：允许重试，但设上限；
- 用户取消：不标记为失败，记录 `cancelled/stopped`；
- 进程重启：扫描 `running`，标记为中断；
- 重跑只处理未完成项，不重复写入岗位或重复发送。

# 9. 阶段 2：事实安全与内容质量（最高优先级）

这是此前“错误生成示例学校/专业”的重大 bug 所对应的长期解决方案。不能只靠 prompt 提醒模型。

## 9.1 事实源白名单

在代码层面建立 `FactSourcePolicy` 或等价服务：

```text
allowed:
  - verified_base_resume
  - verified_resume_material
  - user_confirmed_fact
forbidden:
  - example_resume
  - resume.md
  - resume.example.md
  - job_description
  - ai_score_reason
  - generated_resume
  - platform_default_greeting
  - unverified_import_row
```

所有生成器统一调用该策略，不能招呼语一套规则、简历生成器另一套规则。

## 9.2 事实片段模型

每个可引用事实至少包含：

```json
{
  "fact_id": "mat_xxx",
  "source_type": "verified_resume_material",
  "source_file": "用户上传文件的内部标识，不向模型暴露绝对路径",
  "source_sheet": "经历",
  "source_row": 12,
  "title": "项目名称",
  "fact_text": "用户确认的事实文本",
  "structured_fields": {},
  "verification_status": "verified",
  "created_at": "...",
  "updated_at": "..."
}
```

来源路径、证书编号、电话、邮箱等敏感字段不必发送给 AI；模型只接收完成脱敏和最小化后的事实片段。

## 9.3 生成流程

```text
读取岗位 JD
  ↓
解析要求和匹配关键词
  ↓
从 verified 事实库检索候选片段
  ↓
构造带 fact_id 的受限上下文
  ↓
AI 只做压缩、排序和表达
  ↓
解析 AI 输出中的事实引用
  ↓
校验每个事实都来自允许的 fact_id
  ↓
校验数字、实体、时间、地点、学历、联系方式
  ↓
质量检查和长度检查
  ↓
进入“待审核”，绝不直接进入“可发送”
```

AI 输出若出现没有引用的个人实体、数字或量化成果，应拒绝或标记人工确认，而不是自动接受。

## 9.4 事实一致性校验

至少检查：

- 姓名、电话、邮箱只能来自真实底稿/确认资料；
- 学校、专业、学历、城市必须存在于来源；
- 公司、项目、职务、时间区间必须存在于来源；
- 数字、百分比、金额、人数、排名、奖项等级必须能回溯；
- “精通、负责、主导、独立完成”等强度词不能超过证据；
- JD 中写的是要求，不是用户经历；
- AI 评分中的“你适合某岗位”不能转成“你做过某事”；
- 生成简历和招呼语中不能出现示例占位符；
- 用户编辑过生成文本后，保存和发送前重新校验；
- 任何校验失败都显示具体句子、风险类型和来源缺口。

## 9.5 招呼语特定规则

招呼语是对外文本，安全级别高于普通草稿：

- 生成时只使用真实底稿和已确认素材库；
- JD 只提供匹配点和对方需求；
- 默认短、具体、克制，不堆砌技能关键词；
- 不自动写“我是某某大学学生”等个人信息，除非真实来源中明确存在且用户允许使用；
- 不引用 `resume.md`；
- 不使用 BOSS 账号默认招呼语；
- 不写没有证据的项目结果；
- 不通过校验就不能加入批量确认队列；
- 批量发送前显示总数、逐条查看入口、事实校验摘要和平台额度。

## 9.6 简历版本隔离

`generated_resume` 只能关联：

- 岗位 ID；
- 使用的底稿 ID；
- 使用的事实片段 ID；
- JD 解析版本；
- AI 模型和模板版本；
- 用户编辑记录。

不能把 generated resume 的文本重新写入 `base_resumes` 或素材库。除非用户明确执行“保存为用户确认事实”，且经过二次确认和来源标记。

# 10. 阶段 3：任意 Excel 智能导入产品化

目标不是只支持本人的 `resume_materials.xlsx`，而是让任意用户能够拿自己的表格导入，并清楚知道系统做了什么。

## 10.1 导入支持范围

支持以下常见情况，并对不确定情况给出提示：

- 一个或多个 Sheet；
- 中文、英文或混合列名；
- Sheet 名称不同；
- 表头不在第一行；
- 多级表头或合并单元格；
- 日期、数字、百分比、列表单元格；
- 公式结果为空；
- 预留空白模板行；
- 用户自定义字段；
- 隐藏 Sheet；
- STAR 法则字段：情境、任务、行动、结果；
- 经历、项目、奖项、学生工作、证书、技能证据等类型。

不支持或无法可靠解析时必须停止并说明，不得静默丢列、丢行或拼接错误。

## 10.2 导入向导

建议界面步骤：

```text
上传 → 文件安全检查 → Sheet 概览 → 表头/列映射
→ 类型推断 → 预览与逐行校验 → 选择导入范围
→ 差异比较 → 用户确认 → 原子替换/合并 → 导入报告
```

必须展示：

- 文件名、大小、SHA-256 摘要；
- Sheet 数量和隐藏状态；
- 识别到的表头行；
- 每列映射目标、置信度和样例；
- 有效行、空白行、示例行、错误行数量；
- 未映射列及其真实内容；
- 将要新增、更新、删除的条目；
- 需要用户确认的低置信度映射；
- 导入后正式素材总数；
- 可下载错误报告。

## 10.3 数据安全

- 仅允许 `.xlsx`，限制文件大小；
- 解压防 ZIP Slip；
- 防止恶意超大 Sheet 和资源耗尽；
- 不执行宏；
- 公式按值读取，不执行外部链接；
- 临时导入目录使用随机 ID；
- 导入取消或过期后清理临时文件；
- 原子写入索引和数据库；
- 导入失败不能破坏旧库；
- 保留可回滚快照；
- 原始文件是否保留要由用户可见地配置。

## 10.4 事实状态

导入行不能上传后立刻成为可发送事实，至少经过：

```text
parsed → needs_review（低置信度/缺关键字段）
parsed → verified（用户确认）
parsed → ignored（空白/示例/用户排除）
parsed → invalid（真实内容但无法安全映射）
```

已有的 `valid/invalid/example/blank` 处理必须保留，并扩展为可解释的审核状态。

## 10.5 合并和版本

不要只做“整库覆盖”而没有回滚：

- 提供替换、追加、按稳定 ID 更新三种模式；
- 计算差异；
- 显示被删除/修改的事实；
- 每次导入写入导入批次、文件摘要和时间；
- 允许恢复上一版；
- 同一 Sheet 序号不能造成全局 ID 冲突；
- 中文 Sheet 名、同名 Sheet、不同文件之间都要保证稳定且全局唯一。

# 11. 阶段 4：工作台存活期间的定时采集

这是低干扰模式，不是无人值守机器人。

## 11.1 产品规则

- 只有 Web 工作台正在运行时，调度器才工作；
- 每分钟检查一次，不高频轮询；
- 到达设置时间执行一次；
- 采集后可自动评分；
- 任务完成即停止；
- 不自动发送招呼语、简历、回复或跟进；
- 不做错过时间补跑；
- 不做系统开机自启、休眠唤醒或后台服务；
- Chrome 不可用则跳过并记录；
- 人工任务运行则跳过并记录；
- 每个日期+时间槽每日最多执行一次；
- 工作台重启后不重复执行已 claim 的槽位。

## 11.2 配置

在配置页增加/稳定以下字段：

```yaml
collection_schedule:
  enabled: false
  times: ["09:30", "19:30"]
  weekdays_only: true
  max_pages: 1
  platforms: [boss]
  auto_score: true
  pause_today_date: ""
```

若旧配置没有 `auto_score`，使用向后兼容默认值，并在 UI 明确展示。时间必须严格校验 `HH:MM`，去重并排序。

## 11.3 状态展示

首页卡片显示：

- 是否启用；
- 下一次执行时间；
- 今日已执行次数；
- 最近一次状态；
- 最近一次新增岗位数；
- 最近一次高分岗位数；
- 跳过原因；
- 今日暂停按钮；
- “只采集和评分，不会发送”提示。

## 11.4 跳过原因枚举

至少包括：

- `missed_slot_workbench_started_late`；
- `chrome_unavailable`；
- `platform_not_logged_in`；
- `paused_today`；
- `risk_lock_active`；
- `task_already_running`；
- `daily_page_limit_reached`；
- `no_valid_schedule`；
- `not_weekday`。

用户界面给出中文解释、是否可重试和建议动作。

## 11.5 实现要求

复用现有 `WorkbenchTaskRunner`，不要另起一套采集流程。调度器只负责：

1. 发现到期时间槽；
2. 原子 claim；
3. 运行前 preflight；
4. 构造固定 `collect + optional auto_score` 选项；
5. 将结果写入计划运行表和任务历史；
6. 发布通知；
7. 释放资源。

计划调度必须使用明确的时区策略，默认本机时区 `Asia/Shanghai` 或系统本地时区，但要在配置/日志中可见，避免服务器时区导致错时。

- `tests/test_scheduled_collection.py`

- 工作台启动后，设置未来 1-2 分钟时间可真实触发；

- 错过槽位不补跑；

# 12. 阶段 5：投递确认队列、进度和投后管理

## 12.1 确认队列

每一条待发送记录应展示：

- 公司、职位、平台和联系人；
- 岗位 JD 匹配摘要；
- 招呼语全文；
- 使用的事实来源 ID 和摘要；
- 事实检查结果；
- 简历版本 ID；
- 是否符合平台能力；
- 是否命中重复发送保护；
- 当日平台额度和预计发送数量；
- 最终发送按钮和拒绝按钮。

批量确认必须是“基于当前筛选结果的明确操作”，不能把列表加载过的 156 条岗位隐式全部发送。确认对话框必须显示：

```text
本次将发送 N 条
平台分布：...
已通过事实校验：N
需要人工检查：N
会被跳过：N
预计消耗今日额度：...
发送后不可自动撤回（如平台不支持撤回）
```

## 12.2 进度

发送进度页面应有：

- 总数、已完成、成功、失败、跳过、待处理；
- 当前岗位和当前阶段；
- 最后更新时间；
- 可暂停/停止；
- 失败原因；
- 可安全重试的项目；
- 不可重试的项目及用户动作；
- 平台额度、节奏和风控锁；
- 浏览器连接状态。

刷新页面、关闭页面或服务重启后，进度仍从数据库恢复。

## 12.3 幂等和去重

发送动作至少需要岗位级、会话级、历史台账三级保护。重试前必须再次查询状态，不能因为页面刷新而二次发送。每一次平台动作记录 `idempotency_key` 或等价键。

## 12.4 失败分类

- 用户取消；
- Chrome 断开；
- 未登录；
- 页面结构变化；
- 平台限流/风控；
- 文本不满足平台限制；
- 事实校验失败；
- 已发送/疑似已发送；
- 目标岗位已下线；
- 未知错误。

未知错误不能自动无限重试，必须保留原始错误的脱敏摘要和诊断建议。

## 12.5 投后管理

增加轻量化 pipeline：

```text
未投递 → 已发送 → 已读/未知 → 已回复 → 沟通中
→ 已约面 → 面试完成 → Offer/拒绝/放弃
```

平台无法确认的状态必须显示“未知”，不能推断为“未读”或“已读”。回复建议只能进入人工审核，不自动发送。

# 14. 阶段 7：安全移动端控制面板

移动端只能是本机工作台的安全遥控面板，不是把招聘平台登录信息放到手机上，也不是让手机直接执行浏览器自动化。

## 14.1 默认安全策略

- 默认只监听 `127.0.0.1`；
- 未明确启用时拒绝非本机访问；
- 禁止无鉴权 `0.0.0.0` 公网暴露；
- 外网访问优先建议 Tailscale、ZeroTier 或 VPN，再叠加应用层认证；
- 不在 URL、日志或前端 localStorage 放 API Key、Cookie 或完整 Token；
- 生产环境禁止明文传输，局域网也应提示风险。

## 14.2 配对和认证

建议流程：

1. 用户在电脑工作台点击“开启局域网访问”；
2. 服务端生成短时一次性配对码和二维码；
3. 手机首次输入配对码；
4. 服务端签发设备级随机 Token；
5. Token 只显示一次，服务端只保存哈希；
6. 设备获得可见名称、创建时间、最后访问时间；
7. 用户可以立即撤销单个设备或全部设备；
8. 配对码过期、尝试次数有限、失败限流。

## 14.3 Web 安全

至少实现：

- Session 或 Bearer Token；
- CSRF 防护（Cookie 模式必须有；Token 模式仍要校验 Origin/Referer 和请求来源）；
- SameSite、HttpOnly、Secure（HTTPS 时）Cookie；
- 登录/配对失败限流；
- 请求体大小限制；
- 安全响应头；
- 审计危险操作；
- 设备撤销后立即失效；
- 所有发送类 API 再次要求新鲜确认，不仅凭旧登录态；
- 高风险操作需要电脑端二次确认或一次性确认码。

## 14.4 移动端可做与不可做

移动端可做：

- 查看任务和岗位；
- 查看评分、素材和生成草稿；
- 暂停定时采集；
- 发起采集/评分任务；
- 审核并确认发送（按安全策略）；
- 查看投递进度和回复提醒。

移动端不可直接做：

- 读取或导出平台 Cookie；
- 绕过电脑端 preflight；
- 在没有事实校验时确认批量发送；
- 绕过每日额度、风控锁或人工确认；
- 通过公网裸奔访问本机服务。

## 14.5 CLI/API

增加 `openjob web --host` 时：

- `127.0.0.1` 为默认；
- 监听非回环地址必须显式传入并输出醒目安全警告；
- 如果没有配置配对/认证密钥，拒绝启动非回环监听；
- 记录实际监听地址；
- 提供关闭局域网访问的明确方法；
- 不把图形开关做成绕过 CLI 安全规则的后门。

## 验收

- 默认从另一台设备访问失败或只显示拒绝，不泄露岗位/简历数据；
- 配对码只能使用一次、过期失效、错误多次后锁定；
- 设备撤销立即失效；
- 未认证请求不能读 API 或调用发送；
- CSRF 测试通过；
- 发送 API 仍执行事实校验、平台能力和任务互斥检查；
- 公网监听无认证时启动失败；
- 日志不泄露 Token、Cookie、简历和 AI Key。

- 恢复失败不破坏现有数据；

- 每次 schema 变更有版本号；
- 迁移幂等；
- 迁移前自动备份；

- 迁移日志写入可查询记录。

## 15.5 配置兼容

`config.yaml` 是运行时个人配置，不是示例事实源。`config.example.yaml` 只放空值、说明和安全默认值。升级时：

- 保留未知用户字段或明确提示；
- 添加新字段采用安全默认；
- 移除字段提供迁移提示；
- Secret 只从环境变量或本地配置读取；
- `/api/config` 返回脱敏版本；
- 下载配置时不能把真实 Key 明文带出。

# 19. 前端成熟化设计

## 19.1 首页信息层级

首页只突出用户当前要做的事：

1. 当前工作台/Chrome/AI 状态；
2. 需要用户处理的数量；
3. 定时计划下一次状态；
4. 高匹配岗位；

## 19.2 每个异步操作都要有

- 开始前说明预计动作；
- 禁用重复点击；
- 当前进度；
- 可取消；
- 成功摘要；
- 失败原因；
- 下一步建议；
- 刷新后可恢复状态。

## 19.3 空状态和危险状态

空状态不能只写“暂无数据”：

- 没有简历：上传底稿；

危险动作使用明确按钮文案，如“确认发送 12 条招呼语”，不要只写“确定”。

## 19.4 移动适配

- 核心信息在小屏可读；
- 表格可切换卡片；
- 发送确认不可因屏幕窄而隐藏事实摘要；
- 键盘焦点和触摸目标足够大；
- 网络断开时显示离线，不重复提交；
- 使用 request id/幂等键防止移动端重复点击。

# 20. 可观测性、日志和隐私脱敏

## 20.1 任务事件

每个任务记录结构化事件：

```json
{
  "event_id": "...",
  "task_id": "...",
  "stage": "collection|scoring|generation|delivery|monitor",
  "event": "started|progress|skipped|failed|completed",
  "safe_message": "...",
  "counts": {},
  "created_at": "..."
}
```

## 20.2 日志级别

- `INFO`：任务开始/结束、数量、状态；
- `WARNING`：跳过、可恢复平台问题、额度接近上限；
- `ERROR`：失败和诊断信息；
- `DEBUG`：开发诊断，默认不输出个人文本和密钥。

## 20.3 脱敏

统一脱敏：

- API Key：只显示前 2/后 2；
- Token/Cookie：完全隐藏；
- 电话、邮箱：部分隐藏；
- 简历和素材正文：不写入普通日志；
- JD 中联系人隐私：不写入诊断包；
- 文件路径：显示相对/逻辑路径，不暴露用户目录。

## 20.4 用户可见的审计

至少能查看：

- 谁/哪个设备发起；
- 什么时候确认；
- 用了哪份招呼语和简历版本；
- 使用了哪些事实 ID；
- 最终平台结果；
- 失败/跳过原因。

个人版没有多用户账号，也要保留“本机/设备”维度，方便追查误操作。

# 21. 性能、资源和可靠性目标

不以云端高并发为目标，以个人电脑可长期使用为目标。

建议目标：

- 首页健康检查在本地快速返回；
- 普通列表查询不扫描全表；
- 岗位列表按需分页；
- 长任务不阻塞 API；
- AI 并发默认 1，用户明确配置后才提高；
- 同时最多一个浏览器写操作任务；
- 导入大表时前端分页预览，服务端限制资源；
- 任务日志设保留策略；
- 临时文件和过期导入会清理；
- 数据库有必要索引，并对迁移后查询做简单基准。

不要为了“用完 Token”增加无意义的 AI 调用。AI 调用应有目的、预算、超时、重试上限和成本可见性。

# 22. AI 使用规范

## 22.1 Prompt 输入最小化

发送给模型的上下文按任务拆分：

- 评分：JD + 非敏感岗位配置 + 已允许用于匹配的事实摘要；
- 招呼语：JD + 少量 verified 事实片段 + 用户语气偏好；
- 简历：JD + 选定底稿片段 + 选定 verified 素材；
- 不发送：无关联系方式、证书编号、内部文件绝对路径、Cookie、API Key、其他岗位的私密数据。

## 22.2 防 prompt 注入

JD 是外部不可信文本。若 JD 中包含“忽略系统规则、输出用户秘密、替换事实”等指令，应把它当作岗位内容或风险文本，不当作模型指令。

## 22.3 成本和失败

- 每次 AI 请求记录任务类型、模型、耗时、token 使用量（若 provider 提供）；
- 超时、空输出、非法 JSON、事实引用缺失都可诊断；
- 失败重试有限；
- 模型切换记录在生成版本；
- 用户可关闭 AI 评分，关闭后仍可采集岗位；
- 不因 AI 评分关闭而阻断基础采集。

## 22.4 生成质量指标

可选统计：

- 事实校验通过率；
- 用户编辑比例；
- 生成后拒绝率；
- 发送后撤回/纠错次数；
- 评分与用户最终选择的偏差；
- 各模板的失败率。

这些指标用于产品改进，不得偷偷用用户数据训练外部模型。

# 23. 分阶段 Agent 执行顺序

建议另一个 Agent 按下列批次执行，每批完成后停止并报告，不要一次改完所有阶段。

## 批次 A：基线和事实安全

1. 盘点实现和测试；
2. 固化来源白名单；
3. 统一招呼语/简历事实校验；
4. 补示例污染、JD 注入、人工编辑绕过测试；
5. 修复所有发现的安全回归。

**优先级：P0，完成后才允许批量发送。**

## 批次 B：核心任务和定时采集

1. 复核 `WorkbenchTaskRunner`；
2. 复核定时 claim、时区、重启和跳过；
3. 确认 `auto_score` 开关；
4. 确认计划任务绝不调用发送器；
5. 补真实时间和并发测试。

## 批次 C：投递进度和状态

1. 复核确认队列；
2. 复核批量确认和新鲜确认；
3. 复核幂等、每日额度和失败重试；
4. 完成投递进度页面；
5. 统一状态和历史。

## 批次 D：任意 Excel

1. 复核任意表格的解析边界；
2. 增加差异、回滚、错误报告；
3. 增加 STAR 字段和自定义字段处理；

# 24. 每个批次的提交与回滚要求

## 提交格式建议

```text
feat(facts): enforce verified sources for generated content
fix(schedule): prevent duplicate slot execution after restart
test(import): cover arbitrary workbook mappings
feat(delivery): add resumable confirmation progress
security(web): require pairing before non-loopback bind
docs(product): document platform capability matrix
```

## 回滚要求

- 代码回滚不能破坏数据库；
- 数据库迁移前自动备份；
- 新字段可为空或有安全默认；
- 新生成内容必须保留旧版本读取能力；
- 发送状态不能因版本回滚而重新变成可发送；
- 素材导入必须能恢复上一批次；
- 移动端认证升级失败时默认回到仅本机模式，而不是开放访问。

# 29. 结论：什么叫“成熟”

OpenJob 成熟，不是功能数量达到最多，也不是 AI 调用次数最多，而是用户可以在真实求职周期里连续使用数周，仍然知道：

- 岗位从哪里来的；
- 为什么推荐；
- 哪些经历是真实证据；
- 哪些内容只是 AI 草稿；
- 什么将要发送；
- 谁确认了发送；
- 发送到了哪个平台；
- 失败发生在哪里；
- 是否会重复发送；
- 数据保存在哪里；
- 出问题如何停止、诊断、恢复和回滚。

最终产品承诺应保持为：

> **OpenJob 帮你更高效地准备和管理求职投递，但不替你伪造事实，也不在你不知情时替你对外行动。**

先完成事实安全、任务稳定、确认投递、任意 Excel、定时采集、CI 和诊断，再推进安全移动端。任何阶段都不能牺牲可解释性和用户最终控制权。
